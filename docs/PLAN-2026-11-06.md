Words used below:

- **PR (pull request)**: a set of changes on a branch, waiting to be merged into `main`.
- **main**: the branch the live site runs. Merging into `main` redeploys the live site within a few minutes.
- **e2e test**: a script that opens real headless iPhone-sized WebKit (Safari's engine) windows and clicks through the game.
- **Unit test**: a script that checks the rules or the server with no browser.
- **Rebase**: replay a branch's changes on top of the newest `main`, fixing any overlaps.
- **Runner**: who does a task. Claude on a cheaper model, a Cursor cloud agent, or Brian.

**Why games get wiped.** Rooms live in server memory. Without `REDIS_URL`, `store.js` saves them to `data/rooms.json` on the server's own disk. On Render's free plan that disk is erased whenever the service restarts, redeploys or wakes from sleep (free services sleep after about 15 minutes with no visitors, per Render's free-plan rules as of my training data; tonight's 12-second first answer fits that). Players then see "Game was reset." Three practical rules follow:

- Never merge a PR while the family is playing. Each merge redeploys.
- Open the link a minute before game night so the server is awake.
- For storage that survives restarts, `store.js` already supports Render Key Value (Render's Redis service) with no code change: create one, then add its URL as `REDIS_URL` on the "ostriches" service. As of my training data Render lists a free Key Value plan, which does not save to disk but does survive web-server restarts and deploys. Confirm the price in the dashboard before creating it (Decision B5). Brian asked for no-cost options (D1), so do not pick a paid plan without his yes.

**Smaller risks from the code review that stay open.** One 576-line `server.js` wires four modes by hand. No limit on room creation or message rate (fine for family use). Both are later work, not first wins.
